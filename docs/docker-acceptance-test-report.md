# Docker Acceptance Test Report

**Project:** XM Company Service  
**Date:** 2026-08-13  
**Test type:** Manual end-to-end acceptance test of the Dockerized application  
**Result:** **PASS**

## 1. Purpose

This report records the final end-to-end acceptance testing performed against the Dockerized Company Service.

The goal was to validate the packaged application as an evaluator or operator would run it, including:

- Docker image build and Compose startup;
- PostgreSQL startup and migration execution;
- health endpoints;
- JWT authentication boundaries;
- CRUD behavior for two independent companies;
- validation and conflict handling;
- strict JSON and media-type handling;
- request body limits;
- UUID handling;
- persistence across application restart;
- behavior during PostgreSQL outage and recovery;
- request-ID propagation;
- operational logging;
- graceful shutdown;
- isolated test cleanup.

The acceptance run used a dedicated Compose project so that existing development data and volumes were not affected.

## 2. Test Environment

The acceptance stack was started with an isolated Compose project:

```bash
export COMPOSE_PROJECT_NAME=xm-final-acceptance
unset CONFIG_FILE

export JWT_SECRET='at-least-32-byte-secret-value-1234'
export JWT_ISSUER='xm-company-service'
export JWT_AUDIENCE='xm-company-service'
export LOG_LEVEL=DEBUG

make stack-up
```

The stack contained:

- `company-service`;
- PostgreSQL 17.10 Alpine;
- one-shot database migration container.

A separate isolated Compose project, `xm-final-shutdown`, was later used to verify graceful shutdown independently.

## 3. Test Data

Two companies were created:

### Company A

```json
{
  "name": "Alpha Tech",
  "description": "Software company",
  "amount_of_employees": 12,
  "registered": true,
  "type": "Corporations"
}
```

### Company B

```json
{
  "name": "alpha tech",
  "amount_of_employees": 0,
  "registered": false,
  "type": "Cooperative"
}
```

The names intentionally differed only by case to verify that name uniqueness is case-sensitive.

Both companies received different server-generated UUIDs.

## 5. Detailed Results

### 5.1 Docker build, startup, and migration

The application image built successfully.

After startup:

- PostgreSQL became healthy;
- the migration container exited with code `0`;
- the Company Service became healthy;
- the service was exposed on port `8080`.

Result: **PASS**

### 5.2 Health endpoints

With PostgreSQL available:

```http
GET /health/live
```

returned:

```http
200 OK
{"status":"ok"}
```

and:

```http
GET /health/ready
```

returned:

```http
200 OK
{"status":"ok"}
```

Result: **PASS**

### 5.3 Authentication

Mutation endpoints were verified as protected.

The following cases returned `401 Unauthorized` with `WWW-Authenticate: Bearer`:

- POST without an Authorization header;
- POST with an invalid JWT;
- POST with an expired JWT;
- DELETE without authentication.

A malformed JSON body sent without authentication still returned `401`, confirming that authentication is evaluated before request-body parsing on protected routes.

Authenticated requests using a token generated by `make dev-token` succeeded.

Result: **PASS**

### 5.4 Create and public GET

Company A was created successfully with:

```http
201 Created
```

The response included:

- the complete company representation;
- a server-generated UUID;
- a `Location` header containing the created resource path;
- an `X-Request-ID` response header.

Company B was also created successfully.

Its omitted description was returned as:

```json
"description": ""
```

and the explicit values:

```json
"amount_of_employees": 0,
"registered": false
```

were accepted.

Both companies could be retrieved without authentication using:

```http
GET /v1/companies/{id}
```

Result: **PASS**

### 5.5 Case-sensitive uniqueness

The following names were both accepted:

```text
Alpha Tech
alpha tech
```

This confirms the locked case-sensitive uniqueness rule.

Attempting to create another company named exactly:

```text
Alpha Tech
```

returned:

```http
409 Conflict
```

with error code:

```text
COMPANY_NAME_CONFLICT
```

Result: **PASS**

### 5.6 PATCH behavior

Company A was patched with:

```json
{
  "description": "",
  "amount_of_employees": 0,
  "registered": false
}
```

The response was `200 OK`.

The subsequent GET confirmed that:

- `description` became `""`;
- `amount_of_employees` became `0`;
- `registered` became `false`;
- omitted fields such as `name` and `type` remained unchanged.

This verifies the required distinction between omitted fields and explicitly supplied zero values.

Result: **PASS**

### 5.7 PATCH conflict preserves state

An attempt was made to rename Company B to the exact existing name:

```text
Alpha Tech
```

The request returned:

```http
409 Conflict
```

A subsequent GET confirmed that Company B remained unchanged.

Result: **PASS**

### 5.8 Validation

The following requests were rejected with:

```http
400 Bad Request
```

and error code:

```text
INVALID_REQUEST
```

Scenarios verified:

- empty PATCH object;
- negative `amount_of_employees`;
- `description: null`;
- invalid company type;
- blank/whitespace-only name;
- name longer than 15 characters.

Rejected updates did not corrupt the stored company state.

Result: **PASS**

### 5.9 Media type and JSON handling

The following behavior was verified:

| Scenario | Result |
|---|---|
| Missing `Content-Type` on PATCH | `415 Unsupported Media Type` |
| `Content-Type: text/plain` | `415 Unsupported Media Type` |
| `application/json; charset=utf-8` | Accepted |
| Malformed JSON | `400 Bad Request` |
| Unknown JSON field | `400 Bad Request` |
| Wrong JSON field type | `400 Bad Request` |
| Top-level `null` | `400 Bad Request` |
| Multiple/trailing JSON values | `400 Bad Request` |
| Client-supplied `id` on create | `400 Bad Request` |

Result: **PASS**

### 5.10 Request body limit

A POST body larger than 1 MiB was sent.

The service returned:

```http
413 Request Entity Too Large
```

with error code:

```text
CONTENT_TOO_LARGE
```

Result: **PASS**

### 5.11 UUID behavior

A malformed path ID:

```text
not-a-uuid
```

returned:

```http
400 Bad Request
```

A syntactically valid UUID that did not exist returned:

```http
404 Not Found
```

with error code:

```text
COMPANY_NOT_FOUND
```

Result: **PASS**

### 5.12 Persistence across application restart

The `company-service` container was restarted while PostgreSQL and its volume remained intact.

After the service became ready again, both Company A and Company B were successfully retrieved with their previously persisted values.

Result: **PASS**

### 5.13 PostgreSQL outage and recovery

PostgreSQL was stopped while the application remained running.

During the outage:

```http
GET /health/live
```

continued to return:

```http
200 OK
```

while:

```http
GET /health/ready
```

returned:

```http
503 Service Unavailable
```

with error code:

```text
SERVICE_UNAVAILABLE
```

PostgreSQL was then restarted.

Readiness recovered to `200 OK`, and persisted company data remained available.

This confirms the intended distinction between liveness and readiness.

Result: **PASS**

### 5.14 Delete behavior

DELETE without authentication returned:

```http
401 Unauthorized
```

Authenticated DELETE of Company A returned:

```http
204 No Content
```

A subsequent GET returned `404 Not Found`.

Deleting Company A did not affect Company B.

Deleting Company A a second time returned `404 Not Found`.

Company B was then deleted successfully with `204 No Content`, and its subsequent GET returned `404 Not Found`.

Result: **PASS**

### 5.15 Request-ID propagation

A valid caller-supplied request ID was sent:

```text
11111111-1111-4111-8111-111111111111
```

The same value was returned in the `X-Request-ID` response header and appeared in the HTTP request-completion log.

Result: **PASS**

### 5.16 Operational logging

With `LOG_LEVEL=DEBUG`, the following logs were observed.

Database startup:

```text
msg="database connection established"
duration=<duration>
max_conns=10
```

Database operations:

```text
msg="database operation completed"
operation=create_company|get_company|update_company|delete_company
company_id=<uuid>
duration=<duration>
```

HTTP completion:

```text
msg="http request completed"
request_id=<uuid>
method=<method>
path=<path>
status=<status>
duration=<duration>
```

The inspected service logs did not expose request payloads, company free-text values, Authorization values, JWTs, database credentials, database URLs, SQL text, or SQL arguments.

Result: **PASS**

### 5.17 Graceful shutdown

The graceful-shutdown test was run separately using the isolated Compose project:

```text
xm-final-shutdown
```

Before shutdown, readiness returned `200 OK`.

The service was stopped using:

```bash
docker compose stop company-service
```

Docker reported:

```text
status=exited exit_code=0
```

No graceful-shutdown failure log was emitted.

This confirms that normal container SIGTERM handling completes successfully.

Result: **PASS**

### 5.18 Cleanup and isolation

The acceptance stacks used dedicated Compose project names and disposable PostgreSQL volumes.

Cleanup completed successfully using:

```bash
docker compose down -v --remove-orphans
```

The acceptance-test containers, network, and isolated PostgreSQL volume were removed without affecting the normal development project's database volume.

Result: **PASS**

## 6. Notes

During the first acceptance run, the intended explicit graceful-shutdown command was accidentally concatenated with a preceding shell command and therefore did not execute as intended.

No application failure occurred.

The graceful-shutdown scenario was subsequently rerun independently from a fresh isolated Docker stack and passed with container exit code `0` and no shutdown-failure log.

## 7. Conclusion

The Dockerized XM Company Service passed the final manual acceptance test.

The test demonstrated that the packaged service:

- starts cleanly with PostgreSQL and migrations;
- enforces its authentication boundary;
- implements the required company CRUD behavior;
- preserves the defined validation, uniqueness, PATCH, and error contracts;
- persists data correctly;
- exposes meaningful health behavior during dependency failure;
- propagates request IDs and emits useful operational timing logs;
- shuts down cleanly under the normal container stop signal.

**Final acceptance result: PASS**
